## Context

候选解析、RAG 匹配和客户端展示兜底分别维护服装正则，其中“西装”会先于“裤”命中，详见 `proposal.md`。该修复跨越共享领域逻辑、服务端工作流和 Client Component，但不涉及持久化结构。

## Goals / Non-Goals

**Goals:**

- 让新决策中的品类分组、召回槽位、证据角色保持一致。
- 用可独立测试的共享函数处理关键词重叠。
- 保留现有公开类型和 API 数据形状。

**Non-Goals:**

- 不更新历史 `assessment_reports.outfit_combinations`。
- 不修改 AI Prompt、决策模型或衣橱中的用户确认品类。

## Decisions

1. **抽取共享分类模块。** 候选解析、RAG 和客户端兜底统一调用纯函数，避免复制正则。相比仅调换 `workflow.ts` 的判断顺序，这能同时消除候选解析和前端的同类缺陷。

2. **采用从具体到宽泛的优先级。** 先识别连衣裙、连体裤和套装，再识别裤装/裙装，然后识别外套，最后识别普通上衣。明确名称优先于其中的宽泛词根，因此“西装裤”不会被“西装”截获。

3. **后端以分组生成槽位角色。** `bottom` 槽位再细分裤装和裙装展示文字；前端仅在新数据缺少 `role`/`badge` 时使用共享分类作为兜底。

4. **不触碰历史角色。** 页面继续优先保留历史报告已有字段，符合用户允许自行删除历史错误数据的选择。

## Risks / Trade-offs

- [新的未知品类仍可能无法分类] → 保留 `unknown` 和“可搭单品”兜底，并通过明确测试扩展规则。
- [共享模块进入客户端包] → 模块仅包含小型纯函数和正则，不引入服务端依赖。
- [历史错误仍会显示] → 属于明确非目标，用户自行删除；新记录不再产生同类错误。
