## Context

见 `proposal.md`。当前上传逻辑位于大型客户端组件中：每件原图先经过文件读取、Supabase Storage、记录插入和签名 URL，随后视觉识别与展示图 Route 并行执行。两条 Route 只记录失败摘要，没有统一关联 ID、阶段耗时或标准响应头；展示图片使用 CSS background，也没有资源加载完成信号。

客户端与服务端时钟不能直接相减，视觉识别与展示图又是并行分支。因此需要在每个运行环境内记录相对开始时间和持续时间，再通过关联 ID 合并观察，而不是试图构造跨机器的绝对时间线。

## Goals / Non-Goals

**Goals:**

- 用统一、可测试的轻量计时模型记录嵌套和并行阶段。
- 让一次上传可以从浏览器控制台、Network 响应头和 Vercel 日志交叉定位。
- 对成功、早期返回和异常路径都输出安全、一致的诊断结构。
- 保持业务请求数量和用户可见行为不变。

**Non-Goals:**

- 本阶段不压缩图片、不调整并发、不引入任务队列或外部 APM。
- 本阶段不修改上传交互、状态文案、按钮可用性或视觉样式。
- 本阶段不承诺降低耗时；它只建立后续优化所需的可靠基线。

## Decisions

### 1. 使用共享的单调时钟 trace 工具

新增纯 TypeScript 计时工具，以 `performance.now()` 为默认时钟，并允许测试注入时钟。每个 span 保存名称、相对 trace 起点的开始偏移、持续时间和结果状态。trace 支持并行 span，数值在输出前统一舍入，避免各处自行计算导致口径不同。

替代方案是直接散落 `Date.now()` 与 `console.time()`。该方式难以测试、无法稳定表达并行偏移，也容易在异常路径遗漏收尾，因此不采用。

### 2. 每件衣服使用 trace ID，每个 Route 使用 request ID

客户端在读取文件前生成 trace UUID，通过 `X-Closet-Trace-Id` 同时传给视觉识别与展示图 Route；两条请求再各自生成 request UUID，通过 `X-Request-Id` 传递。服务端只接受合法 UUID；缺失或非法时生成新 UUID，避免把任意头内容写入日志。

同一 trace ID 关联两条并行 Route，request ID 区分具体 HTTP 请求。批量上传时每件衣服各有独立 trace，避免共享计数污染。

### 3. 服务端同时提供 Server-Timing 与单条结构化日志

每条 Route 在返回时生成 `Server-Timing`、`X-Closet-Trace-Id`、`X-Request-Id`，并输出一条带固定前缀的 JSON 汇总。浏览器 Network 面板适合查看单次请求，Vercel 日志适合跨阶段检索；两者复用同一份 span 快照。

不为计时结果写 Supabase，也不接入新的监控 SDK。额外远程请求会污染被测链路并增加失败面，因此当前不采用。

### 4. 客户端记录整体与服务端边界，不合并跨时钟绝对时间

客户端记录文件读取、原图上传、记录插入、签名 URL、AI HTTP 请求与响应解析、最终映射和总耗时，并保留响应的 `Server-Timing` 原文作为关联证据。服务端各自记录内部阶段。汇总展示每个环境内的 duration 和 offset，不从服务端时间戳减去客户端时间戳。

### 5. 最终图片加载使用真实图片元素事件

现有 CSS background 没有 load 事件。保持相同固定尺寸和 `object-cover` 视觉效果，将衣橱图片渲染为实际 `<img>`，仅为新上传且有活跃 trace 的展示图记录第一次 `load` 或 `error`。回调只完成计时，不改变成功状态或阻塞页面。

### 6. 白名单元数据与一次性日志

日志固定包含 trace ID、operation/route、结果、总耗时、span 列表和经过审查的字节数或 provider/model 名称。禁止把请求体、错误原文、URL、认证头和用户内容合并进汇总。每条 Route 至多写一条日志，客户端每件衣服至多写一条最终汇总，控制日志开销。

### 7. 在展示图供应商边界拆分响应体读取与 JSON 解析

展示图供应商 `fetch` 返回响应头后，先在 `provider_response_body_read` span 中读取响应文本并计算 UTF-8 实际字节数，再在 `provider_response_json_parse` span 中执行 JSON 解析。这样可以把供应商首字节等待、响应体传输和应用侧解析分别观察，不再由 `response.json()` 合并后两段。

供应商响应诊断只允许记录 HTTP 状态、数值化的 `Content-Length`、实际响应字节数、经过长度和字符限制的请求 ID，以及只保留 metric 名称和 duration 的 `Server-Timing`。请求 ID 只从明确列出的响应头名称读取；完整响应头、响应正文、接口 URL、图片/Base64 和提示词均不进入日志。

该拆分不增加任何供应商调用、Storage 操作或数据库写入。`Content-Length` 可能描述压缩传输长度，而实际响应字节数按 Fetch 解压后的 UTF-8 文本计算，两者只用于诊断，不要求相等。供应商响应头到达前的内部排队、推理与网络等待仍只能合并在 `provider_fetch_ttfb` 中；若供应商未返回自身 `Server-Timing`，应用侧无法进一步可靠拆分。

## Risks / Trade-offs

- [浏览器关闭或资源长期不加载导致客户端汇总不完整] → 为展示图 load 设置非阻塞超时，并以 `timeout` 状态结束 trace。
- [平台或代理裁剪 `Server-Timing`] → Vercel 结构化日志保留同一份服务端数据，响应头不是唯一来源。
- [日志量增加] → 每个 Route 只输出一条小型汇总，不记录逐阶段日志或图片内容。
- [替换 CSS background 产生细微渲染差异] → 保留原固定高度、宽度、圆角、cover 与 center 规则，并通过桌面和移动端截图验收。
- [监控代码异常影响业务响应] → 格式化、日志和客户端资源回调必须失败隔离，不能改变原有 HTTP 状态或上传结果。
- [供应商诊断头包含异常或过长内容] → 只读取固定白名单，对请求 ID、计时名称和数值执行长度、字符与有限数检查；无效值直接忽略。

## Migration Plan

1. 在 Preview 部署计时版本，完成单件成功、供应商失败和批量上传验证。
2. 检查 Network 中的响应头、浏览器汇总和 Vercel 日志是否能用关联 ID 对齐。
3. 采集至少数次真实上传，记录各阶段中位数与最大值，再更新本 change 的后续优化任务。
4. 若诊断产生异常，可删除计时调用和响应头；没有数据库迁移或持久数据需要回滚。
