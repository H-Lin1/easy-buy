## Context

衣橱视图位于 `src/app/app/page.tsx`，当前关键词匹配已提取到 `src/lib/closet/filter-items.ts`，五个顶部筛选控件仍是静态按钮。`ClothingItem` 已提供品类、颜色、风格标签、季节标签、穿着频率和生命周期状态，因而本变更可以在客户端对已加载的完整衣橱集合进行筛选，不需要改变 Supabase 查询或 AI 流程。

## Goals / Non-Goals

**Goals:**

- 为五个筛选维度提供可访问的多选交互，并让选项和当前衣橱数据保持一致。
- 用纯函数统一处理关键词、结构化筛选、数组标签、状态映射和季节兼容规则。
- 保持筛选结果、待确认面板和全量统计之间的作用域边界清晰。
- 让清除单个条件、已选维度一键清除、重置全部条件和无结果恢复行为可测试。

**Non-Goals:**

- 不把筛选下推到 Supabase，也不新增查询参数、API 或数据库字段。
- 不建立新的服装分类词典；品类、颜色和风格继续使用现有自由文本值并做轻量规范化。
- 不修改上传、AI 识别、衣服确认或购买决策流程。
- 不在本次变更中加入排序、分页、拼音搜索或模糊推荐。

## Decisions

### 在客户端复用纯筛选逻辑

将筛选状态作为一个明确的值对象传入现有匹配逻辑，保持“输入完整衣橱、返回卡片集合”的纯函数边界。空查询和所有维度均为“全部”时返回完整集合；这样既保留已有关键词测试，也能用确定性用例覆盖组合条件。

备选方案是为每个按钮分别在组件内过滤。该方案会重复匹配规则，难以保证关键词与结构化筛选始终使用相同的 AND 语义，因此不采用。

### 维度内 OR、维度间 AND

每个维度保存一个已选值数组。字符串字段（品类、颜色）匹配任一选中值；数组字段（风格、季节）匹配任一标签；五个维度之间以及关键词与结构化筛选之间都取交集。这与用户的多选预期一致，也能表达“通勤或休闲风格的白色上衣”这类查询。

### 选项来源与规范化

品类、颜色和风格选项从完整 `items` 集合提取、去除空值并按去首尾空格和英文大小写去重。季节和穿着状态使用固定的用户可见选项，避免某次筛选后菜单选项消失。显示值保留首次出现的原始中文，比较值使用规范化文本。

备选方案是从当前已过滤集合生成选项，但连续选择条件会使选项动态消失，用户无法方便地调整已选条件，因此不采用。

### 明确状态和季节语义

用户可见的“状态”映射到 `wearFrequency`：`often` 为常穿、`sometimes` 为偶尔穿、`rarely` 为闲置、`unknown` 为待确认；`active/idle/archived` 仍作为内部生命周期字段，不直接暴露为筛选项。季节值为春、夏、秋、冬和四季；一件“四季”衣服在选择任一具体季节时命中，而选择“四季”只匹配四季标记。

### 使用多选菜单而不是横向展开所有值

每个顶部按钮打开一个带复选项的菜单，按钮文本显示已选数量或简短的当前值摘要。未选值时触发器显示展开提示；存在已选值时，触发器右侧显示独立的 `X` 清除按钮，替代展开提示。点击 `X` 只清除当前维度并阻止菜单打开，点击触发器其余区域仍可打开菜单。该按钮提供可访问名称和键盘焦点样式。菜单使用可访问的展开状态和键盘关闭行为，选项过多时在菜单内部滚动；搜索框和卡片网格的布局保持不变。重置全部操作只在存在条件时显示或启用。

## Risks / Trade-offs

- **自由文本造成语义重复** → 仅做空白和英文大小写规范化；同义词归并留给后续分类词典变更。
- **筛选选项较多导致菜单过长** → 菜单限制高度并在内部滚动，不改变卡片网格布局。
- **历史数据缺少季节或穿着频率** → 缺失值不报错；季节条件不命中缺失标签，状态缺失归入“待确认”。
- **现有关键词调用方依赖旧函数形态** → 保留无筛选参数时的原有行为，并用回归测试锁定空查询、大小写和标签匹配。
- **完整集合与显示集合混用导致统计错误** → 选项、待确认面板和统计始终从完整 `items` 计算，只有卡片网格使用过滤结果。

## Migration Plan

无需数据迁移或环境变量变更。实现完成后运行纯函数测试、lint、生产构建，并在桌面和移动端验证菜单、多选组合、清除和无结果状态。部署失败时可直接回滚本次应用提交；由于没有 schema 或 API 变更，回滚不会影响已有衣橱数据。
