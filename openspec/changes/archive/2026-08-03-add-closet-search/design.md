## Context

`ClosetView` 已经拿到当前用户的完整 `ClothingItem[]`，并在同一 Client Component 中渲染待确认面板、卡片网格和穿着频率统计。现有搜索区域只是静态控件；本次行为契约见 `specs/closet-search/spec.md`。

衣橱数据已经包含搜索所需字段，因此搜索不需要新的请求或持久化状态。首个试点还需要一个不依赖 Supabase 登录态的确定性验证入口。

## Goals / Non-Goals

**Goals:**

- 将搜索状态限制在 `ClosetView` 内，避免扩大父组件和数据加载逻辑的职责。
- 将匹配规则抽成纯函数，使字段范围和输入规范化能够独立测试。
- 保持待确认面板和底部统计继续读取完整 `items`，只有卡片网格读取搜索结果。

**Non-Goals:**

- 不持久化搜索词，不同步到 URL，也不跨页面保留搜索状态。
- 不为小规模本地数组引入索引、防抖、服务端检索或第三方搜索依赖。
- 不同时实现页面上尚未启用的五组属性筛选器。

## Decisions

### 1. 在 `ClosetView` 中维护受控搜索状态

`ClosetView` 使用本地 `query` state，并通过 `useMemo` 从 `items` 派生 `filteredItems`。这能让输入、结果数和清除操作共享单一状态，同时确保上传或删除导致的 `items` 更新会自动反映在结果中。

备选方案是把查询状态提升到 `Home`、写入 URL 或发送到服务端。它们会增加跨组件接口、导航语义或网络状态，而当前搜索只服务于已加载的单个页面，因此不采用。

### 2. 使用独立纯函数定义匹配规则

新增 `filterClosetItems(items, query)`：先对查询执行 `trim()` 和 `toLowerCase()`，空查询直接返回原列表；非空查询对名称、品类、颜色及三类标签逐字段执行包含匹配。字段值使用相同的小写规范化，中文内容保持不变。

备选方案是在 JSX 中直接拼接并过滤，代码更短但难以覆盖边界测试，也容易让显示逻辑与字段规则耦合。当前数据量较小，逐次线性扫描比建立索引更简单且足够可靠。

### 3. 区分两种空状态并保留全量统计

真实空衣橱继续使用现有首次上传引导；仅当 `items` 非空、规范化查询非空且 `filteredItems` 为空时，显示搜索无结果状态和清除按钮。激活搜索时显示“找到 X 件，共 Y 件”，底部常穿/偶尔穿/闲置统计仍由完整 `items` 计算。

这样用户能分辨“没有数据”和“当前条件没有结果”，同时不会误以为搜索改变了衣橱总量。待确认面板也继续基于完整 `items`，避免搜索隐藏需要用户处理的数据质量任务。

### 4. 用 Node 内置测试验证匹配契约

为纯函数新增基于 `node:test` 的 TypeScript 测试，覆盖空查询、各字段、标签、首尾空格、英文大小写和无匹配。项目当前使用 Node 24，可以直接执行 TypeScript 测试，无需引入测试框架；应用层再通过 lint、生产构建和浏览器交互完成验证。

## Risks / Trade-offs

- [每次输入都线性扫描完整衣橱] → MVP 衣橱规模有限；若未来出现明显性能问题，再以真实数据决定是否索引或防抖。
- [简单包含匹配不支持拼音、同义词或错别字] → 在输入提示和非目标中保持预期明确，避免首个试点引入不可预测的搜索语义。
- [登录门禁可能限制自动化 UI 验证] → 核心匹配规则由纯函数测试覆盖，并结合 lint、生产构建；在可用登录态下补充浏览器验收。

## Migration Plan

无数据迁移。部署仅包含前端代码和测试文件；回滚时移除搜索状态、匹配工具及对应测试即可，不影响已有衣橱数据或接口。
