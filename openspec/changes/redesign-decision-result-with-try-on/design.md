## Context

参见 `proposal.md` 的动机与范围。当前决策接口同步完成文字报告并将 `outfit_combinations` 保存到 `assessment_reports`；前端收到报告后再保存包含完整 report 快照的聊天消息。现有衣橱展示图接口已经实现鉴权、超时、输出校验、私有存储上传和失败清理。当前生产配置已切换为 Tripo/OpenAI-compatible image-edit API，并通过 multipart `image[]` 接收图片。

现有搭配结构没有稳定标识，规则兜底也可能产生一套用于说明的伪搭配。试穿生成必须区分真实模型搭配与兜底内容，并保证并行任务完成顺序不会打乱 UI 中的图片和来源单品。

## Goals / Non-Goals

**Goals:**

- 让决策接口先完成并返回文字报告，随后由独立请求生成试穿图。
- 对最多 3 套有效搭配提供稳定身份、统一通用模特、并行执行、整体揭示、持久化与幂等重试。
- 复用当前 Tripo/OpenAI-compatible 图片供应商配置与私有 Supabase 存储，不引入第二套图片基础设施。
- 保持历史聊天可恢复，且试穿失败不影响已保存的决策结论。

**Non-Goals:**

- 第一版不提供用户模特、体型参数驱动的拟真合身判断或尺码准确性承诺。
- 不扩展“更多灵感”来突破每份报告最多 3 套的限制。
- 不逐张流式展示完成结果，也不把生成图片作为真实上身效果的保证。

## Decisions

### 0. 无图片输入先进入独立的补图引导模式

`/api/ai/assess-purchase` 在鉴权和请求校验后首先检查本次请求是否包含图片。纯文字请求不再从文字猜测候选商品，也不生成向量、不读取衣橱、不创建候选商品或报告；接口改为返回带显式 `image_required` 模式的简短助手回复。服务端使用独立的强约束提示词调用决策模型，只允许模型说明需要上传商品截图或照片，以及可补充价格、场景和犹豫点。用户原始文字被标记为仅供理解的非指令内容，避免其中的提示注入改变分流结果。

模型输出还会经过本地结果护栏：必须包含上传/提供图片的明确动作，且不得包含购买结论或声称已经看过商品；空内容、越界内容和模型异常统一降级为固定的友好补图文案。前端将这类结果作为普通用户/助手消息持久化，历史对话按助手消息元数据恢复，不渲染耗时、决策报告、状态操作或真人试穿。带图片请求继续进入原购买分析链路。

### 1. 文字报告与试穿生成采用两个请求

`/api/ai/assess-purchase` 继续负责识别、检索、决策和报告持久化。前端收到报告并渲染结论后，再调用新的 `/api/ai/generate-outfit-try-ons`。新接口以 `reportId` 为主键从服务端读取候选商品、搭配和衣橱图片，不信任客户端提交的任意存储路径。

选择该方案是因为图片生成耗时和失败率明显高于文字决策，拆分后结论可尽快返回，图片失败也不会回滚报告。备选方案是在评估接口中等待图片完成，但会直接增加首屏结果延迟且耦合失败域，因此不采用。

### 2. 为搭配补充稳定 outfitId，并限制有效搭配

工作流在规范化模型输出后，为最多 3 套真实搭配补充稳定 `outfitId`。首版有效条件为：`usedModel` 为真、存在候选截图、`visualIntent` 为 `outfit`、至少有一个有效 `closetItemId`。兜底搭配保留给文字解释，但不进入试穿生成。

`outfitId` 同时写入报告 JSON 和聊天快照，作为 UI 绑定、数据库唯一约束与重试定位键。使用数组下标作为持久身份的备选方案在新增或过滤搭配后容易错配，因此仅保留 `position` 用于排序，不用作唯一身份。

### 3. 使用固定模特资产和原生多图输入

仓库保存一张中性背景、正面全身的通用成年真人模特图片。服务端不再使用 `sharp` 将引用图缩放拼成单张参考板，而是通过当前 Tripo/OpenAI-compatible multipart image-edit 协议重复提交 `image[]`：Image 1 为固定模特、Image 2 为待买商品、Image 3 及之后为该套衣橱来源单品。

提示词为每个位置定义稳定角色：模特图只提供身份、身体比例、姿势、构图、光线和背景，必须忽略并替换其原有服装；待买商品图是颜色、材质、纹理、图案、轮廓和结构细节的首要视觉事实来源；衣橱单品按搭配顺序逐件使用且不得遗漏、重复或替换。文字元数据与图片视觉冲突时以对应服装图片像素为准。该方案避免参考板缩放造成的候选服装像素损失和模特原服装视觉权重过高。当前不再为 SiliconFlow 单图协议保留试穿生成兼容分支。

### 4. 服务端并行、all-settled、按源顺序返回

接口先解析并验证最多 3 套任务，再使用 `Promise.allSettled` 同时执行。每个任务独立生成、校验、上传并提交数据库状态。聚合层始终按报告的 `position` 返回，不采用 promise 完成顺序。

只有全部任务为 ready 时，响应才包含可展示的完整图片集合。任一任务失败时等待其余任务结束，返回聚合失败状态、各任务状态和来源信息，但不返回部分成功图片 URL。重试时跳过 ready 行，只 claim failed/pending 行。

### 5. 独立表持久化生成状态和溯源信息

新增 `outfit_try_on_images` 表，字段包括 `user_id`、`report_id`、`outfit_id`、`position`、`closet_item_ids`、`image_path`、`status`、`model`、`prompt_version`、`failure_kind`、时间戳，并以 `(report_id, outfit_id)` 唯一约束。开启 RLS，仅 owner 可访问。输出继续保存到私有 `purchase-screenshots` bucket 的 `<userId>/try-ons/` 前缀。

使用独立表便于 claim、重试、观测和历史恢复，也避免每个并行任务竞争更新整块 `assessment_reports.outfit_combinations` JSON。聊天消息继续保存文字 report 快照；打开历史对话后通过试穿接口读取最新图片状态。

### 6. UI 采用两段式结果、单行思考流程和成套切换

结果区不再渲染评分卡、星级、候选商品报告或重复大图，也不显示“结论”标签、独立的 `decisionLabel` 或“已保存到最近对话”提示。非空对话页头移除“决策助手”标题，只保留说明文案，并同步收紧标题移除后的顶部空间；说明文案复用购买结论正文的文字颜色，其与页头底部分割线的间距再缩短约一半。分析阶段以单行、不换行的流程链展示，已出现的相邻阶段通过箭头连接；当前阶段使用动态标识和轻量强调，完成后退回纯文字。窄屏时只允许流程容器自身横向滚动，并在分析期间自动跟随最新阶段，避免撑宽页面。分析完成后的耗时小于一分钟时只显示秒数，达到一分钟后才显示分和秒；耗时文字单独位于一条完整分割线上方，正文区域不再绘制额外顶部边线。耗时秒数随助手聊天消息元数据持久化，打开未来历史对话时只读取这一真实字段并恢复同一分割栏；旧消息没有显式秒数时不显示也不推算耗时。非空对话页头的底部分割线缩进至内容边界，与结果正文中的分割线采用一致的左右留白。回答正文取消居中的窄宽度容器，与耗时区域共享相同左右边界；`summary` 不再单独限宽，右侧与下方依据区域对齐。摘要到依据、依据到穿搭、穿搭标题到方案以及穿搭到决策操作等宏观垂直间距缩小约一半，但保留列表和单品卡内部的可读间距。第一段直接呈现 `summary`、相关理由和风险；摘要与主要依据之间不显示分割线，并在移除横线后保持当前垂直间距；依据区与穿搭区域之间只保留一条分割线。第二段只使用黑色“穿搭效果”标题；生成中显示紧凑加载状态，全部成功后以套数切换控件呈现当前搭配。桌面左侧真人图按生成文件的方形比例贴合显示，不使用会露出容器底色的 `contain` 留白；右侧恢复为包含方案信息、待买商品、衣橱单品、原因标签和摘要的完整卡片，并通过等高网格与摘要置底尽量和左图底部对齐。移动端仍纵向堆叠。

批次失败时仍展示每套来源单品摘要和统一重试按钮，但隐藏部分成功试穿图，符合整体揭示约定。决策状态动作保留在结果末尾，不参与两块主要信息层级。新结果不再默认把“先收藏”表现为已选择，而是在浅主题色操作区显示“为这件衣服选择一个决策状态”，三个按钮初始均未选中。点击“决定买”或“先收藏”成功后显示“已保存到决策清单”、对应选中态和清单入口；点击“暂不考虑”后显示“未进入决策清单”和对应选中态。为了让历史对话仍能恢复“暂不考虑”，该状态继续持久化，但在加载清单时从可见条目、筛选项和侧栏数量中排除。历史对话只恢复数据库中真实存在的状态，不再用“先收藏”兜底。

## Risks / Trade-offs

- [多张图片的角色仍可能被模型混淆] → 固定输入顺序，在提示中逐张声明用途，并禁止继承模特原服装、遗漏或重复来源单品。
- [并行 3 个图片请求产生供应商峰值压力] → 服务端硬限制每批最多 3 个，单任务独立超时并记录失败类别。
- [固定模特身份跨生成仍可能轻微漂移] → 每次将完全相同的模特原图作为 Image 1，并固定构图和提示版本。
- [客户端离开页面导致请求中止] → 已提交的单任务结果会持久化；重新打开或重试时复用 ready 行，只补齐未完成任务。
- [数据库迁移尚未部署时接口不可用] → UI 将其视为试穿批次失败，不影响文字结论；迁移与应用代码可独立回滚。

## Migration Plan

1. 添加固定模特资产、原生多图提示构建器和请求测试。
2. 部署 `outfit_try_on_images` 迁移、索引和 RLS 策略。
3. 部署幂等试穿 API 与类型扩展；旧报告没有 `outfitId` 时按报告内容生成确定性标识，但只为符合有效条件的搭配生成。
4. 部署新的结果 UI，历史报告继续显示文字结论；已有报告可在首次打开时生成试穿图。
5. 回滚时停用前端试穿调用和新结果区；新增表与已存图片可保留，不影响旧报告读取。
